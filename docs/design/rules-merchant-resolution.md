# Rules-first merchant resolution, measured on a frozen synthetic set

## Problem

[Detection](recurring-charge-detection.md) groups charges by merchant, so the merchant behind each narration has to be right. A wrong merchant can merge two subscriptions or hide a price step, and that is worse than no merchant at all. SBI narrations are noisy:
- the payee name and UPI ID are cut short, sometimes losing the `@domain`;
- the fixed-width detail column puts spaces inside words when it wraps;
- the same merchant shows up under brand, legal and gateway names.

There are no real labelled statements yet, and real statements must never enter git.

## Approach

- **Catalogue as code.** `config/merchants.yml` lists merchants with category, payee names and exact UPI IDs. It is reviewed like code and synced into `merchants` / `merchant_aliases` by `leak:merchants:sync`, which `db:seed` also runs.
  - Names are stored as A–Z0–9 keys and UPI IDs in lower case. A check constraint enforces both forms.
  - Households can have their own aliases (from the review queue), and these override the catalogue for that household only.
- **Rules, strongest first** (`Merchants::Resolver`):
  1. exact UPI ID;
  2. payee name: exact, a catalogue name of five or more characters at its start, or a truncation of a catalogue name of six or more characters;
  3. the part of a cut-short UPI ID before the `@`;
  4. for card, NACH and bill-pay text, the longest catalogue name starting at any word, with names shorter than five characters (LIC, OLA) matched only as whole words;
  5. `pg_trgm` similarity ≥ 0.5 that beats every other merchant by ≥ 0.15.

  Bank charges, interest and cash are recognised by pattern. A person needs a personal-looking name plus a phone-number UPI ID, or a consumer-app ID containing the name. Conflicting signals, or no signal, mean **abstain**: the row goes to the LLM step and then, if still unsure, to review.
- **Persistence.** Each bank transaction stores `merchant_id`, `counterparty` (merchant/person/bank/cash), `resolution` (the rule that decided, or `abstained`) and `resolved_at`. Check constraints keep these consistent. The importer resolves rows as it posts them.
- **Evaluation.** The data is synthetic and generated by `Synthetic::Narrations`.
  - Its surface forms are written independently of the catalogue and include forms the catalogue lacks.
  - It damages narrations the way statements do.
  - It includes unanswerable rows: gateway-only payments and unknown shops.

  There is a 600-row dev set for tuning and a 300-row golden set that was reviewed by hand and then frozen by SHA-256. The headline metric is **merchant accuracy at a stated coverage**, over business rows, with 95% Wilson intervals. CI fails if the accuracy lower bound drops below 95% or coverage drops below 75% (baseline: 99.4% [96.8, 99.9] at 76.3%).

## Trade-offs

- Precision over recall: about a quarter of business rows abstain in the synthetic sets. That's the [LLM step](llm-merchant-resolution.md)'s job, and it must beat this baseline on the same golden set.
- Synthetic scores overstate real accuracy. The gate catches regressions; it doesn't promise real-world accuracy. The first real statements will be checked through the review queue, and any new failure modes become new rules or catalogue entries plus new dev rows. The golden set gets a new version, never an edit.
- The catalogue needs maintenance as merchants rename (Zomato → Eternal) or change gateways. Keeping it in YAML means reviewed diffs instead of a hidden admin table.
